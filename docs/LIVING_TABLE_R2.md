# The Living Table R2: Companion Agency & Memory

R2 extends [Living Table R1](LIVING_TABLE_R1.md) in the existing PorchQuest369 repository. The classic adventure, Creator Studio and current browser save key are preserved. The new R2 agency schema is an additive field within the R1 portable save.

## What works

- **Goals:** each companion starts with an authored purpose. While recruited, the player can edit that companion's active goal.
- **Individual memory:** player-authored notes and approved action summaries are stored per character, capped at twelve memories each. Notes have a source, a turn/scene reference and a visibility label, either private to that companion's model context or party-shared.
- **Suggestions:** a recruited companion may offer a locally generated suggestion even without a model, or may ask the server-side AI to produce a strict JSON candidate.
- **Review:** exactly one pending action is staged with the actor, skill, source, description and the exact scene, turn and seed.
- **Approval:** the player explicitly approves or declines. Approval runs the companion's specialized investigation through deterministic dice with a fixed +3 bonus and a rules-derived DC. Successful matching checks may reveal the scene's existing clue. Decline doesn't spend a turn or advance the RNG.
- **Receipts:** accepted and declined proposals are logged. Approved actions create a party-visible character memory. Stale proposals cannot commit.
- **Offline continuity:** JSON save/import restores goals, memories and pending valid proposals. Existing R1 saves migrate to an empty companion notebook without losing the campaign.

## How to try

Run the feature branch locally:

~~~powershell
git clone https://github.com/MichaelWave369/PorchQuest369.git
cd PorchQuest369
git switch feat/living-table-r2-companion-agency
cd apps/web
npm install
npm run test:living
npm run dev
~~~

Enter **The Living Table**, recruit Mira (or another character), and select **Suggest action**. Read the proposal, then **Approve & Roll** or **Decline**. If no model is connected, the proposal will explicitly be labeled **LOCAL** and generated by deterministic rules. To try actual AI suggestions, connect the local FastAPI/Ollama adapter as documented in R1; R2 adds POST /api/living-table/propose and retains POST /api/living-table/say.

Choose a recruited companion in **Companion purpose and memory** to edit goals and save notes. Notes labeled **Selected companion only** enter only that selected character's model prompt, not the Dungeon Master's or another character's. **Party-shared** notes are currently displayed in the recipient's notebook and remain available for future broader party-context adapters. No other companion can currently read them automatically, so the label is a scope for future explicit delivery rather than a claim of live cross-character sharing.

## Rules and privacy boundaries

- The model is a **proposal writer**, not a game-state authority. It cannot choose a skill other than the actor's fixed specialization, mint loot, invent DCs, roll dice or teleport the party.
- Only a recruited character may propose. No more than one proposal can be pending at once; the proposal expires if the canonical turn, location or RNG seed changes.
- The server rejects malformed, extra-field, or non-JSON proposals. A failed model request may produce a clearly labeled rule-based alternative for review, never an automatic action.
- Character notes are **plaintext browser data** and part of the exported JSON. "Private" means scoped AI prompt inclusion, **not** at-rest encryption or an authentication boundary. Treat exported campaigns accordingly.
- Any server-side AI integration sends the selected character's bounded remembered notes to the configured provider. Only connect models/providers you trust. R2 doesn't train or fine-tune model weights.
- No automated, unattended companion turns or model-run background loops. Proposals are requested by a person and require a separate approval click.
- Not yet implemented: semantic memory retrieval, hidden NPC knowledge, true multiuser ACLs, initiative/combat actions, map tokens, autonomous party scheduling, visual world creation or VR acceptance.
